# v1.0.0 release plan

Status: draft, 2026-09-28. Nothing here is tagged or published.

## What 1.0 means for this project

1.0 is a **compatibility promise**, not a feature count. After 1.0, a
breaking change to anything listed under "The contract" requires 2.0. So the
work before 1.0 is: decide every format now, break what needs breaking in
0.x, then prove that real people can use it.

Where we are (2026-09-28): v0.3.2 on PyPI and GitHub Releases, ~120
downloads a month, 157 repo views, 0 stars, 0 issues, README says "no
users yet". The launch drafts in `docs/launch/` have never been posted.
Every download so far is unexplained traffic, not feedback.

## The contract (frozen at 1.0)

Written up as `docs/stability.md` in 0.4.0, and each item gets a golden-file
test that must keep passing through 1.x.

| Surface | Frozen at 1.0 | Today |
|---|---|---|
| CLI | command names, flags, exit codes (0 / 1 / 2 meanings), `--json` output shape | not documented as stable |
| `atp-mcp.yaml` | schema, with a `version:` field | **no version field** |
| `.atp/policies.yaml` | schema, rule kinds, with a `version:` field | **no version field** |
| Regression suite YAML | schema `version: 1` | has `version: 1` |
| Evidence bundle + trace export | format, `atp evidence verify` accepts every 1.x bundle | not versioned |
| Decision vocabulary | outcomes and reason codes (`CAPABILITY_NOT_GRANTED`, …) | stable in practice, not promised |
| Gateway HTTP API (`atp serve`) | `/authorize` request/response | not promised |
| Python API | **only** what `docs/stability.md` names; `atp_*` internals stay private | everything is importable |

Not in the contract: the dashboard, `.atp/` SQLite layout (migrated
automatically), benchmark numbers.

## Phase 1: v0.4.0, the freeze candidate (breaking changes land here)

Everything that changes a file format or wire format has to happen before
1.0, so it all goes in this release.

1. `version:` field in `atp-mcp.yaml` and `.atp/policies.yaml`; files without
   it are read as v1 with a deprecation warning. `atp regression migrate`
   (currently LATER) becomes the single `atp migrate` for all three files.
2. Grants: Ed25519 with a `kid` (O6). This changes the grant format, so it
   can't wait. Key rotation stops invalidating outstanding grants.
3. `REQUIRE_APPROVAL` (O7): a decision nothing can complete shouldn't be in
   a stable vocabulary. **Recommended:** keep the outcome, ship the minimal
   approval path (`atp approve TRACE` signs over the action hash with an
   approver identity and expiry, then re-authorizes and issues a grant). The
   alternative is marking it experimental in `stability.md`.
4. Version the evidence bundle and trace export format; `verify` checks it.
5. A custom 422 handler that stops echoing input (O9). Small, but it's a
   wire-level change.
6. `docs/stability.md`, plus golden-file tests: 0.4 files and bundles
   committed under `tests/compat/0.4/`, which every later release must load.
7. macOS in the CI matrix. It's cheap, and "works on your OS" is part of 1.0.
8. Harden `atp mcp init` output from the first-user test: the `fs:destroy`
   denial is the known first-run stumble. Print the exact line to add.
9. **Cumulative budgets (O8)**, pulled forward from LATER for the
   collaboration below: a delegation carries a spend budget per period as
   well as `max_amount` per action, with reservation semantics (reserve at
   grant, settle on the reported outcome, release on expiry). The design
   constraint is in `docs/research/rejected-ideas.md`. It changes the
   delegation format, so it has to land before the freeze.
10. **Per-human signed authority (O11)**, pulled forward for the same reason:
    each human (or organization) root is its own Ed25519 key that signs its
    root delegation, so the operator key stops standing in for every human.
    This is the minimum needed before another organization could verify a
    chain. Builds on item 2.

Gate: the existing 11-step gate from `v0.3.0-plan.md`, plus the compat tests
and a macOS leg.

## Phase 2: launch 0.4 and get real users (the actual blocker)

A 1.0 promise to nobody is only a claim. The drafts are already written.

1. Publish the drafts in `docs/launch/`: Show HN, r/programming,
   r/LocalLLaMA, X thread, LinkedIn. Update them for 0.4 first (they
   describe 0.2/0.3). Posting is the maintainer's call, one post at a time.
2. Open 5 to 8 real issues from `docs/good-first-issues.md` so the repo
   doesn't look empty to visitors.
3. Directly ask 3 to 5 people running MCP servers (Claude Desktop, Cursor,
   Claude Code users) to run `atp mcp init` on their own server. Record each
   run the way `first-user-test-v2.md` does.
4. Feedback window: at least 3 to 4 weeks. Any format complaint gets fixed
   now, in 0.5, while breaking is still allowed.

**Exit criteria for Phase 2** (all required before 1.0):
- ≥ 3 external people wrapped a server that is not in this repo, recorded
- ≥ 2 upstream MCP servers beyond the reference filesystem server moved to
  "verified" in `docs/integrations/compatibility.md`
- No open issue labelled `format` or `breaking`

## Collaboration demo: ATP on an external simulation engine

A potential collaborator runs an enterprise simulation engine: a simulated
company where an agent can be exposed to operational failures, conflicting
instructions, malicious documents and compromised agents. The long-term idea
is that evidence gathered there informs what the agent is allowed to do in
the real business, with ATP as the enforcement boundary. This is also the
first external user that Phase 2 needs.

### The first joint demonstration

One purchasing workflow, end to end:

1. The agent completes a legitimate purchase inside the engine (ALLOW).
2. A malicious supplier document tries to redirect payment or raise the
   amount past the delegation (the scenario `atp demo injection` already
   runs against a mock).
3. The prohibited transaction is blocked at the execution boundary (DENY,
   before the engine's tool runs).
4. `atp policy explain` shows exactly which constraint failed and who
   authorized what; `atp regression add` pins it; `atp test` passes in CI.

### What each side provides

| Side | Provides |
|---|---|
| Engine | Its purchasing tools and transaction state exposed as an **MCP server** (stdio or Streamable HTTP). No ATP code on their side. |
| ATP | `atp mcp init` + `atp mcp wrap` over that server, a policy set for the purchasing tools (amount, payee, destination account), the regression suite, the recorded demo. |
| Both | One scripted scenario (the malicious document) and one command that runs the whole thing. |

If the engine cannot speak MCP, the fallback is `atp_adapter_http` in front
of its HTTP API. That means more work on the ATP side, so ask first.

### Before any code is shared

- A short written agreement: the joint demo lives in its own repository;
  each side keeps its own IP; ATP stays MIT under its current copyright
  holder; no exclusivity at this stage; who may present the demo publicly.
- Facts to get from the collaborator: the engine's license and stack,
  whether it already exposes MCP, who owns it (person or company), and
  where the transaction state lives.

### What is claimed, and what is not

Claimed (tested in this repository): delegation that can only narrow,
per-action `max_amount`, expiry, argument and scope policies at the
execution boundary, single-use grants over the action hash, a hash-chained
trace, shadow mode, regression tests from recorded decisions.

Not yet claimed (direction, not a feature): cumulative budgets (Phase 1,
item 9), cross-organization verification (needs items 2 and 10, then
verifiable delegation handed across the boundary), authority that
contracts when behavior deteriorates (research), evidence from simulation
feeding authorization automatically (research).

### Done means

- The demo runs from one command against the collaborator's engine, on a
  machine that is neither of ours.
- The engine is listed as *verified* in `docs/integrations/compatibility.md`.
- The run is recorded the way `docs/first-user-test-v2.md` is.

## Phase 3: v1.0.0-rc1, then v1.0.0

1. Pick one adoption feature, driven by Phase 2 feedback. The likeliest
   candidate is **Streamable HTTP served by the proxy with client auth**
   (O15): stdio-only on the served side rules out remote agents. If nobody
   asks for it, it moves to 1.1.
2. Re-run the security review for 1.0 (`security-review.md`) and the red-team
   list. Every High item either gets fixed or stays documented as a
   deployment requirement (O1–O4 stay by design; say so plainly in the 1.0
   notes).
3. Upgrade guide `docs/release/upgrading-to-1.0.md`: 0.3 → 1.0, running
   `atp migrate`.
4. rc1 on PyPI (pre-release), 2 weeks with no format changes, then 1.0.0.
5. README status line changes from "experimental" to "stable; not
   independently audited". Don't drop the audit caveat unless an external
   audit actually happens.

Gate for 1.0.0: the Phase 1 gate, compat tests from `0.4/` passing, Phase 2
exit criteria met, and the upgrade path from a real 0.3.2 `.atp/` tested.

## Explicitly not in 1.0 (additive, so 1.x)

Idempotency key injection · SPIFFE/mTLS and OIDC identity providers · trace
export hook and signed heads · OpenTelemetry · chaos tests · OPA/Cedar
adapters · Docker MCP Gateway / agentgateway modes · Postgres and
multi-instance · TypeScript SDK · dashboard policy-impact view. None of
these changes a frozen format, so none of them block 1.0.
